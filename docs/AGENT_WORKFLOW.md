## Artifact ownership

| Concern | Workflow artifact | YatraCanvas authority |
| --- | --- | --- |
| Long-range product direction | `docs/ROADMAP.md` | Authoritative roadmap and acceptance criteria |
| Current delivery slice | `docs/scope/` | Optional working view created by `/scope`; reconcile with the roadmap |
| Pre-implementation design | `docs/specs/` | Working build specifications created by `/architect` |
| Accepted architecture | `docs/DECISIONS.md` | Authoritative accepted decision record |
| Architecture and provider state | Existing source-of-truth docs | Must use `[IMPLEMENTED]`, `[PARTIAL]`, `[PLANNED]`, `[DEPRECATED]`, or `[UNKNOWN]` |
| Verification and review | `docs/reviews/` | Evidence generated by `/check`; it does not change application code |
| Release and incident prose | `docs/releases/`, `docs/postmortems/`, `CHANGELOG.md` | Generated from repository and incident evidence by `/document` |

Do not initialize `docs/scope/` merely to copy the entire roadmap. Create it when a concrete
next delivery slice is chosen. Do not mark a feature or spec complete solely because a skill
ran; use repository, runtime, migration, and test evidence.

## Recommended brownfield workflow

YatraCanvas is an established Flutter and FastAPI application. Use the skills selectively:

1. Run `/scope <next slice>` when the team has selected a bounded next slice. A `GA` workflow
   tier is the recommended default for user-facing, authentication, provider, database, and
   itinerary changes; record the chosen tier in the generated scope rather than assuming it.
2. Run `/architect <feature>` before changes that require a load-bearing product, data,
   provider, security, or cross-cutting decision. Keep the resulting spec consistent with the
   existing architecture and accepted decisions.
3. Run `/develop <feature>` only after required decisions are explicit. Follow the migration
   rule in root `AGENTS.md`: repository work may create and validate reversible migrations but
   must not apply them to production.
4. Run `/check verify <feature>` against the real app or appropriate integration environment.
   Run `/test` for durable automated coverage. Use `/check review` before merge when an
   independent review is warranted.
5. Run `/document` for PR, changelog, release-note, or postmortem prose when that artifact is
   actually needed.
6. Run `/sync` last to reconcile only facts supported by the change. It may make surgical
   additions to context files, but must not rewrite curated documentation.
7. Run `/debug <symptom>` whenever a reproducible defect needs root-cause investigation.

`/audit` is not required immediately because the repository already has curated context and
source-of-truth documents. Use it only for a specific context gap, and preserve the existing
root instructions.

## Update policy

- Review upstream changes before replacing the installed directories.
- Record the new upstream commit and verification date in this file after an update.
- Re-read changed `SKILL.md` files for conflicts with YatraCanvas rules.
- Validate documentation and inspect the Git diff before committing an update.
- Do not let upstream workflow conventions silently introduce dependencies, providers,
  environment variables, migrations, or claims about implementation status.
